# alldot 性能实测（2026-11-26）

> 本机 10.0.19045 x64，Node 24.13.0。
> 所有数字是当场测的，不引用旧记录里的推测。

## 本次实测

| 项目 | 数值 | 方法 |
|---|---|---|
| 桥 token + 状态查询（brain_status） | 156 ms | `curl` 打 `/mcp`，从发请求到拿到完整 JSON |
| 派一个最小任务（brain_task 返回任务号） | 79–86 ms | 同上，计时到 HTTP 响应 |
| 状态轮询单次响应 | 232–250 ms | 任务执行中反复查 brain_status |
| 任务开始动工 | 约 3.5 秒 | 从派单到状态变「执行中（第 1 个里程碑）」 |
| 任务走到第 2 个里程碑 | 约 10 秒 | 同上轮询 |
| 简单建文件任务到终态 | 约 29 秒（第二次）/ 5 秒（第一次失败终止） | 轮询到状态「终止」 |
| 任务消耗 token | 23208（第二次）、约 2 万级 | 账本 tasks.spent_tokens |

**端到端体验**：派单本身几乎即时（80 ms），用户真正等的是工人执行。一个"建一个文件写一句话"的最小任务，从发出到出结果约 30 秒，其中前面约 10 秒在拆里程碑和准备，后面是模型逐步调用工具。

## 两个真任务都产出了文件

- `D:/tmp/perf-probe/perf.txt`（5 字节）
- `D:/tmp/perf-probe/ok.txt`（2 字节）

但账本都判 `failed`，原因不是没干成：工人顺手调 `files/list` 列工作区父目录 `D:/tmp`（在工作区 `D:/tmp/perf-probe` 之外）被路径围栏拒了一步，文件本身在后续步骤写出来了。这是**任务失败判定与产物不一致**，不是性能问题。

**已修（2026-11-26）**：`dispatch/settle.ts` 改成只读探测失败（`side_effect=safe`，status=failed）不算致命。写类失败（replayable/unknown）、`interrupted`、`rolled_back` 仍一票否决；良性失败写进 `state_reason` 留痕，没有成功步照样 `failed(no_steps)`。这样"列错目录但文件写成"会判 `done`，真正写失败不受影响。已同步到 `build/package/alldot-dist` 安装副本。两名新测试守住边界（只读失败+写成功→done；interrupted 即使 safe 仍 failed）。

## 旧账本统计（81 个任务，441 步）

| 指标 | 数值 |
|---|---|
| 步骤耗时 p50 / p90 / p99 | 0.0s / 0.9s / 187.4s |
| 模型调用 400 次 | 输入 137 万 / 输出 11 万 token |
| 任务状态 | done 38 / failed 35 / cancelled 4 / 待批 4 |

p50=0 说明多数步骤是瞬间完成的工具调用（判档、记账），不代表用户等到回复的时间。p99=187 秒说明少数长任务确实慢。failed 里混着大量测试任务，不能当生产成功率。

## 冷启动（深入定位 + 已做的优化）

停掉 `dot-keeper`，杀掉网关进程，干净重启，轮询 18789 到响应。

| 轮次 | 到端口可用 | 网关日志自报 ready |
|---|---|---|
| 优化前 | 221 秒 | — |
| 关 sherpa 下载 | 202 秒 | — |
| 关 context 阻塞预热 | 222 秒（HTTP 仍被渠道初始化拖住） | **48.7 秒** |

**根因（实测确认）**：`ensureContextWindowCacheLoaded()` 单独计时 **121.5 秒**。它内部 `ensureAllBotModelsJson` 去做 provider catalog 网络发现，端点不通就等超时。网关在 `server.impl` 里 `await` 它，所以 HTTP server 一直起不来。

**已做的优化（都有备份，时间后缀 20261126-172010）**：

1. `~/.allbot/gateway.cmd` 加 `SHERPA_ONNX_AUTO_DOWNLOAD=0`，省掉 GitHub 下载失败空等 107 秒。
2. `C:\allbot-public\dist\server.impl-jukwAG4x.js`：把 `await ensureContextWindowCacheLoaded()` 改成 `void ...()` 后台预热。网关自报 ready 从 157 秒降到 **48.7 秒**。
3. `~/.allbot/allbot.json` 删掉 stale 插件 `openclaw-lark`（配置里引用但插件不存在）。

**为什么端口可用仍要 200+ 秒**：网关自报 ready 后还有 `starting channels and sidecars`，飞书 `open.feishu.cn` 的 tenant_access_token 请求 30 秒超时、model-pricing bootstrap 30 秒超时，这些串行拖住 HTTP 响应。它们跟 dot 无关，且受网络环境影响。

**因此改走「界面先起、后台等」**：`chat.html` 加了启动状态轮询。页面是静态文件秒开，顶部徽章先显示「服务启动中… ⏳」，每 3 秒打 `/health` 探大脑状态，就绪后自动变「就绪」并拉任务列表。启动中发任务会明确提示"服务还在启动中，等就绪再发"，不再报含糊错误。这条比继续压启动时间更实际。

**顺手修的真 bug**：`/chat` 原来用 `new URL(...).pathname` 拼文件路径，在中文路径上变成 `/C:/Users/1/Documents/%E7%A0%94...`，`readFileSync` 找不到 → 一直 404（独立桥 8799 上尤其明显）。改用 `fileURLToPath`，已验证页面正常返回。

**48 秒的 41 秒静默段（打点实测）**：`starting...` 后打点 A0→A2 耗时 32–34 秒，卡在 `prepareGatewayStartupConfig` 里的 `activateRuntimeSecrets`。试过两项，都**无效并已回滚**：
- 清空 `plugins.entries` 做对照：仍是 34 秒 → 跟插件条目无关。
- 明文 token 时跳过第一次 `activate:false` 预检：ready 从 48.7 变 49.1 秒 → 不是它，真瓶颈在第二次 `activate:true`（真激活 secrets，不能跳过）。

结论：这 34 秒是上游 secrets 快照的固定开销，需要改 `allbot-public` 的 secrets 实现才能真正降下来，单纯配置/跳过预检无效。当前保留的有效优化只有 context 预热后台化（157→48.7 秒）。真正解决用户体感的是界面先起 + 启动中提示。

**更大的开机问题**：`dot-keeper` 计划任务只有 TimeTrigger（每 5 分钟），缺 LogonTrigger / RestartOnFailure / StartWhenAvailable。`keeper-install.ps1 -Execute` 能装完整版，但本机非管理员会话被拒。要开机自动拉起需管理员跑一次（命令见脚本输出）。

服务状态：网关 HTTP 200、桥 health ok、keeper Ready。615 条测试全过。
