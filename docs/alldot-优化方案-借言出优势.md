# alldot 优化方案：借言出（Mika）已经跑通的机制

> 2026-11-26。目的：alldot 的内核比言出硬（账本、闸门、结算），但用户看得见的那一层比言出薄很多。
> 这份方案只做一件事：把言出验证过的「产品化机制」搬到 alldot 上，不重做内核。
> 所有 alldot 现状都有实测出处；言出侧的机制来自源码调研，落地前要再核对一遍接口。

## 一、判断基线

alldot 现在是一个"只会干活、不会说话"的执行器：

- 账本十二张表、tier 闸门、任务契约、结算规则、看门狗，这套治理是它比言出硬的地方，方案不动。
- 但它的用户界面只有一个 `build/dot-core/src/bridge/chat.html`（内联脚本），配置靠手写 JSON，出问题只会写日志。
- 2026-11-26 晚实测：一句「只回两个字：收到」建了任务、零步骤、账本判 `failed(no_steps)`，页面卡片同时显示「完成 ✓」。

言出反过来：界面和引导做得厚（364 个 UI 文件、312 个测试文件），但它只能在手机上干活，任务账本和治理几乎是空的。

所以方案的方向是：**内核继续用 alldot，产品层照言出的做法补。**

## 二、alldot 现状的九处硬伤（有实测出处，不是推测）

### 1. 没有"对话"通道

`dispatch/settle.ts` 里「零步骤不算成功」是刻意的规矩（注释写明"零步骤当成功是错的"），但整套链路里没有任何一处负责"这个问题直接由模型回答"。
结果：用户随口问一句，被当成任务派下去，工人无事可做，判 `failed(no_steps)`。
证据：账本 `task_d3ef5a8dc658c05d016e7eaf`，`state=failed`，`state_reason=会话结束但一步都没做（no_steps）`。
现状代码里 `brain_task / brain_status / brain_answer / brain_cancel` 四个工具（`bridge/tools.ts`），没有第五个用于纯对话。

### 2. 失败原因写给模型看，人看不懂

账本里的 `state_reason` 实例：

> `工人会话报错：这一步做不了（workspace_missing）：这个任务没说往哪个文件夹做（任务声明里没有 workspace / root / workdir / dir），原话里也没点名桌面 / 文档 / 下载 / 图片或一个现成的路径。要让这只手干活，要么把工作区写进任务声明，要么在话里说清往哪儿做；手不猜、也不默认到桌面。`

这段话对工人模型是有效的（它下次知道要声明工作区），但对手机上的用户是噪音：他不知道"任务声明"是什么，也没有地方写。

### 3. 界面是一页内联脚本，坏了就是白屏

2026-11-26 手机端实测：聊天页被套上状态页那套 `default-src 'none'` 的 CSP，页面里所有内联脚本和 `onclick` 被拦，`send()` 根本没定义，用户看到的是"点发送按钮没反应"，没有任何报错提示。
同类风险还在：`chat.html` 约 900 行内联 JS，没有构建、没有类型、没有单测，改一处只能靠人肉回归。

### 4. 体检有，但结果到不了用户

`dot-keeper` 每 5 分钟跑一轮，`~/.allbot/dot/state/keep.json` 里 16 行体检结果（green / yellow / red），实测当前状态：

- `red`：上一轮自检没过，`exit=1`（细节一串 PASS/FAIL 文本）
- `yellow`：`没在跑；8797 不通、进程也没找到。脸没开，审批没人点`
- `yellow`：`剩 5091.9 MB；低于 5120 MB`

这些都只落在 JSON 文件里。用户要自己开文件才知道，手机上看不到。

### 5. 配错了是静默失败

`config-schema.ts` 严格拒绝未知字段（`~/.allbot/dot/keeper-start.json` 的 `_说明` 字段就是踩过坑留下的注）。配错一个字段名，插件直接不加载，用户看到的是"服务没起来"，没有任何"你第 3 行这个字段不认识"的提示。

### 6. 审批没有超时，人不在就永远挂着

审批走 `approvals` 表，没有 TTL、没有过期语义，也没有「旧卡片作废」。keeper 那条 yellow 就是这个：「没在跑；8797 不通、进程也没找到。脸没开，审批没人点」。
言出那边的对应规矩是：15 分钟超时按"不同意"处理、绝不自动同意、每次申报用新 key 让旧按钮作废。alldot 这三条一条都没有。

### 7. 错误不分层，最坏情况把 JSON 当回答

`chat.html` 的 `send()` 只认 HTTP 成功，不判 `isError`、不判 JSON-RPC 的 `error`。
实测后果：token 失效时 `bridgeToken=''`，每次发送拿到 401 JSON，`resultText = JSON.stringify(data)`，整段 `{"ok":false,"error":"unauthorized"...}` 被当成助手回答塞进气泡。工具级失败（例如磁盘满返回 `paused_disk`）一样显示成正常回答。
桥这一侧的错误本身是规整的（`{ok:false, error, message}`，401 带 `WWW-Authenticate`），坏在页面没按层区分：网络不通 / 403 `access_denied` / 503 `bridge_token_missing` / 401 / 工具失败 / JSON-RPC 错，六种要有六种说法。

### 8. 网页上根本批不了审批

`chat.html` 里有整套 `.approval-card` 的 CSS（443–491 行），但没有任何代码渲染它、也没有调用 `brain_answer`。
状态页自己也写着「审批入口只有 ds-bot」。也就是说：人在手机上、电脑前没人，任务要审批就只能挂着。

### 9. 「手机端和电脑端功能一致」现在还不成立

那个 Windows exe 独有五块：审批抽屉（同意/拒绝/自动同意 4 档）、体检抽屉（失败分布、待部署补丁、自我优化提案、最常错工具、花费）、对回答的「对了/不对」反馈、补丁部署、自我优化提案处置。
网页和手机一样：只有聊天、进度、任务列表，侧栏任务项还不能点开（`status-running` 是写死的圆点）。
所以昨晚那个「替换入口就等于功能一致」的说法要收回：入口换了，功能面对齐还差这一步。

## 三、九条可搬的做法（言出怎么做 → alldot 缺什么 → 改哪里）

### 1. 把"回答"和"干活"分成两条路

- **言出**：模型回答和开任务本来就是两条路，用户问一句话不会被当成任务派下去。
- **alldot 现在**：只有 `brain_task`。任何输入都建任务，纯问答必然 `no_steps` 失败（账本 `task_d3ef5a8d…` 是实例）。
- **改哪里**：`bridge/tools.ts` 加第五个工具 `brain_reply(intent)`：调同一个大脑模型，**不建任务**，把回答文本直接返回，token 记进 `spend_ledger`（不记账就违背了这套账本的意义）。`chat.html` 的发送默认走 `brain_reply`，回答下面给一个「这活儿让它去做」的按钮，用户点了才走 `brain_task`。
- 为什么先做显式两条路、不做"让大脑自己判断要不要动手"：后者要多一次模型调用、判断错误的代价是用户明明想聊天却被派了任务，而且没法单独测。等两条路都稳定了再合并。
- **怎么验**：一句「只回两个字：收到」→ 拿到回答、账本里**没有**新任务；一句「在 D:/tmp/t 建 a.txt」→ 点「让它去做」后建出任务、状态与页面文案一致。

### 2. 问题分「挡不挡活」两类

- **言出**：`Problem` 分 blocker 与 warning，只有 blocker 拦开工；页面总状态卡只显示最严重的那一条，颜色按是否 blocker 定红黄。
- **alldot 现在**：`keep.json` 只有 green/yellow/red，且不区分"这个黄能不能继续用"。
- **改哪里**：`tools/keeper.ps1` 的每一行体检加 `blocks` 字段（true/false）。磁盘余量、隧道、981 之类不该挡派单的算 warning；网关不通、账本不可写算 blocker。桥新增 `GET /api/doctor` 把同一份结果吐给页面。
- **怎么验**：把 8931 那只浏览器手停掉 → doctor 显示黄但不挡派单；把网关停掉 → 红且发送被拦并说明原因。

### 3. 体检结果送到用户眼前，而不是落在 JSON 里

- **言出**：首页一张总状态卡，点进去是逐项问题 + 修复入口；系统开关用监听回写，用户从系统设置回来自己就变绿了。
- **alldot 现在**：`keep.json` 里 16 行结果没人看。实测此刻就有一项 red（自检 exit=1）、两项 yellow（exe 界面没开、磁盘 5091 MB 低于 5120 阈值）。
- **改哪里**：`chat.html` 顶部徽章从"就绪/启动中"扩成三态，点开是一个体检面板（消费 `/api/doctor`），每行一句话 + 「怎么修」；面板里同一条问题在手机上显示和电脑上一样。行内已有的参照物是 exe 的体检抽屉（失败分布、待部署补丁、最常错工具、花费），网页要的是同一份信息，只是不分两套实现。
- **怎么验**：故意制造一项黄（停 8932）→ 手机页面徽章变黄、点开能看到"干净浏览器没起"，修好后 5 分钟内自己变绿。

### 4. 修复动作是枚举，不是让用户敲命令

- **言出**：`Fix` 是纯枚举，`MainActivity` 统一执行（跳系统页、请求权限、重连助手），UI 只发意图。
- **alldot 现在**：什么都得人到命令行敲（起网关、起手、重连隧道、装计划任务）。
- **改哪里**：定义 alldot 的 fix 动作表：`start_gateway`、`start_hand:<名>`、`restart_tunnel`、`install_keeper_task`、`prune_artifacts`、`clear_report_queue`。全部走 keeper 已有的 action 机制（`keeper-start.json` 里那套），桥上暴露 `POST /api/fix`，页面按钮直接调。要求：每个动作幂等，执行完立刻回读体检结果，不许只回"已执行"。
- **怎么验**：页面点「起网关」→ 30 秒内徽章从红变绿，`keep.json` 里对应行变 green。

### 5. 配错要指出哪一行，而不是静默降级

- **言出**：模型没配会拦住发送并说明缺什么，并且给"去配"的入口。
- **alldot 现在**：其实**已经有了**带键路径的错误——`config.ts` 的 `parseConfig` 会抛 `config.json:<键路径>: …`，多键、类型、范围都报。问题是桥把它吞了：`server.ts:153-161` 用 `try/catch` 包住 `loadConfig`，出错就静默换成 `defaultConfig()`。于是配置写错 = 配置没生效 = 页面一切正常，只有行为悄悄不对。另外 `config-schema.ts` 严格拒绝未知字段，`keeper-start.json` 里的 `_说明` 就是踩坑留的注（把启动命令塞进 config.json 会让插件拒载）。
- **改哪里**：桥不再吞这个异常——把最后一次 `ConfigError` 存进服务状态，`/health` 和 `/api/doctor` 都带上，页面顶部直接显示"`keepalive.tunnelPort` 应该是数字，你写的是字符串"。要允许降级运行也行，但降级必须是**显式的**（页面一直挂一条黄色"配置有错，正在用默认值"），不能像现在这样无声。
- **怎么验**：故意把一个字段名写错 → 页面显示具体字段名并保持黄条，而不是毫无反应。

### 6. 要人点的事必须有超时、会过期、能推到手机

- **言出**：确认 15 分钟超时按"不同意"处理、绝不自动同意；每次申报用新 key，旧通知上的按钮一律作废；接管串行排队，只有队首能接，接上才计时；用户在别的界面时胶囊变橙 + 通知静音照发。
- **alldot 现在**：审批走 `approvals` 表，没有超时；"有人点了"依赖电脑上那个 exe 界面开着（keeper 那条 yellow 就是它），人不在电脑前任务就悬着。
- **改哪里**：审批加 TTL（默认 30 分钟，到期按拒绝写进账本，理由写"超时"）；每条审批带不可复用的 id，页面上旧卡片的按钮点了返回"这条已过期"；桥上把待审批推到手机页面顶部角标 + 现有的飞书通道；exe 界面没开时不该影响手机审批。
- **改哪里**：三件事，按顺序。
  1. 网页先能批：`.approval-card` 的样式已经在 `chat.html` 里躺着了，缺的是渲染 + 调 `brain_answer`。
  2. 加 TTL：默认 30 分钟，到期按拒绝写进账本，理由写"超时"；每条审批带不可复用的 id，旧卡片点了返回"这条已过期"。
  3. 推到手机：待批进页面顶部角标 + 现有的飞书通道；exe 没开不该影响手机审批（现在 exe 不开就等于没人能批）。
- **怎么验**：派一个需要审批的任务，人不在电脑前 → 手机页面能看到"在等你点"，点掉后任务继续；不点等过 TTL → 账本写"超时按拒绝"，任务终止而不是挂住。

### 8. 错误要分层，别把 JSON 当回答

- **言出**：六种失败六种说法（系统版本不够、助手没起、无障碍没开、通知被降级、模型没配、设置被限制），每条都带修复入口，从不把原始报文丢给用户。
- **alldot 现在**：`send()` 不判 `isError`、不判 JSON-RPC `error`；token 失效时整段 401 JSON 被当回答塞进气泡（`resultText = JSON.stringify(data)`）。页面也没有"连不上桥"这一态，网络断了还显示"服务启动中"。
- **改哪里**：`chat.html` 里加一个统一的错误解释函数，把六种情况分开：网络不通 / 403 来源被拒 / 503 没有令牌 / 401 令牌无效 / 工具返回 `isError` / JSON-RPC 错。每种给一句人话 + 一个动作（重试、去拿令牌、看体检）。把"启动中"和"连不上"拆成两态。
- **怎么验**：故意改错令牌 → 页面说"令牌不对，去电脑上复制 `~/.allbot/dot/bridge-token`"，不是一坨 JSON；断网 → 说"连不上电脑"，恢复后自己重连。

### 9. 网页补齐 exe 那五块，否则谈不上"电脑和手机一致"

- **言出**：手机和电脑是同一个 App，不存在两套功能面。
- **alldot 现在**：exe 有审批抽屉、体检抽屉、回答反馈（对了/不对）、补丁部署、自我优化提案处置；网页和手机一样，只有聊天 + 进度 + 任务列表，侧栏任务项还点不开（`status-running` 是写死的圆点）。
- **改哪里**：这五块逐个搬进网页（exe 和网页消费同一份 `/api/*`，不写两套）：审批（第 6 条）、体检（第 3 条）、反馈（`/feedback` 已经在桥上有路由，页面没调）、任务详情（点开侧栏看步骤与账本）、补丁部署与自我优化提案（先只读展示 + 一个执行按钮，回滚留 keeper）。
- **怎么验**：同一件事在 exe 和手机网页上都能做且结果一致；关掉 exe 只留手机，上面五件事一件不少。

### 7. 自检和诊断写成数据，出一份能复制的报告

- **言出**：自检每项自带超时和依赖，被依赖项没过就记 Skipped 并写明缺哪项，整次 90 秒预算；诊断是固定分节的纯文本，强制脱敏（IP/端口/邮箱/凭据），只给用户看、由用户手动复制或分享，从不自动上报。
- **alldot 现在**：自检结论埋成 keeper 的一行 `exit=1` 加一串 PASS/FAIL 文本；诊断没有面向用户的出口，`state/keeper-report-queue.jsonl` 已经 1.4 MB 没有任何轮转。
- **改哪里**：把自检项写成数据表（每项：名字、超时、依赖、怎么跑、失败的处置建议），跑完生成纯文本报告；桥加 `GET /api/diagnostics` 返回脱敏后的报告，页面上「复制诊断」按钮。顺手给 `keeper-report-queue.jsonl` 加轮转（按大小切、保留 N 份）。
- **怎么验**：健康时跑一次报告全是 PASS；故意停一只手动 → 报告里那一项 FAIL 且写明"修法：页面点『起 8931』"；报告里 grep 不到 token/IP/端口。

## 四、分期与验收

| 期 | 内容 | 做完的标志 |
|---|---|---|
| P0 | 第 1 条（对话通道）+ 第 8 条（错误分层）+ 页面状态与账本一致（现在显示"完成"而账本是 failed） | 手机上问一句话拿到回答；令牌错、断网、任务失败各有各的说法；任何状态文案和账本一致 |
| P1 | 第 2、3、5 条（体检分类 + 体检面板 + 配错提示） | 制造三种故障，手机上都能看出是什么问题、点哪里修 |
| P2 | 第 4 条（fix 动作表）+ 第 6 条（审批 TTL 与推送）+ 第 9 条前四项（审批卡、体检面板、反馈、任务详情进网页） | 人不在电脑前也能审批；点按钮能把红变绿；关掉 exe 只留手机，这四件事都能做 |
| P3 | 第 7 条（自检报告 + 诊断导出 + 报告队列轮转）+ 第 9 条剩余（补丁部署、自我优化提案）+ 计划任务用管理员装一次（现在只有 TimeTrigger，缺开机自启） | 报告能复制发给别人看且不含敏感信息；重启电脑后不用人管就恢复 |

P0 是唯一"不做就没法用"的一条，建议先单独做，做完立刻在真机上验一遍再往下走。


## 五、明确不抄的部分

- **手机侧无障碍 / 虚拟屏 / 内置助手**：言出那套是"用手机操作手机"，alldot 的定位是"电脑上干活"，搬过来没有使用场景，成本极高。
- **Kotlin + Compose 重做界面**：alldot 只需要一页 Web，重做客户端等于把 alldot 变成第二个言出，与"一个大脑一个账本"冲突。
- **把言出的模型配置体系搬过来**：alldot 的模型在电脑上配一次，手机不该再配一遍（这也是这次把 App 首页直接指到 alldot 的原因）。

## 六、验收方式

借言出的做法：每条能力都要有一个端到端的真机/真浏览器用例，不是一个单测就算完。至少覆盖：

1. 服务没起来时打开手机页面 → 明确显示"启动中，别急"，并自动变成就绪（已有雏形，要补真机验证）
2. 纯对话一句 → 拿到模型回答，账本状态与页面显示一致
3. 配错一个字段 → 页面告诉他哪个字段错了，不是"服务没起来"
4. 任务卡在审批 → 手机上能看到"在等你点"，并能点掉
5. 断网 30 秒回来 → 页面自己恢复，不用人刷

### 2026-11-27 补：盘满时「回收器还在睡」（这次差点让整个产品停摆）

重启后桥的 `/health` 里出现 `admission: {allowed:false, reason:"盘紧：账本盘只剩 0.61 GB（低于 0.78 GB），暂停接新任务"}`。顺着查下去，问题不止「C 盘满」：

- keeper 每轮测盘，剩不到 800 MB 就写 `pauseAdmission=true`，dot-core 据此拒新任务。**这是对的**——盘满时写动作会 ENOSPC。
- 但快照回收器（`maintenance.sweepSnapshots`）只认一个上限：`keepalive.snapshots_max_gb`，默认 5 GB。当时快照 1.8 GB，没到上限，**一分钟都没删**。
- 两条规则各管一半：一条说「盘紧就停」，一条说「总量超 5 GB 才清」。中间那块（盘 0.6 GB、快照 1.8 GB）谁也管不到，产品就这么停着。

**修法**：上限改成会跟着磁盘走。新加 `effectiveLimitBytes()`——盘宽裕时就是配置值；盘剩不到 1.5 GB 时按「腾到 2.5 GB」倒推预算，最低保底 256 MB。另外加了一条紧盘巡检，只要还低于 1.5 GB 就再清一次，不用等半小时那一轮。

**顺手踩到自己挖的坑**：第一版把紧盘巡检设成一分钟一轮，然后网关开始卡——`/bridge/status` 有的请求 29 秒才回。原因是快照目录有 18 万个文件，`treeSize` 是同步遍历，一次就把事件循环按住 15～29 秒，手机轮询跟着超时。改成异步版 `sweepSnapshotsAsync`（`fs/promises` 逐个 await，遍历期间让出事件循环），巡检间隔放回 5 分钟，并加了个 `sweeping` 开关防止上一轮没走完又叠一轮。教训：**定时器里不许跑同步遍历大目录的代码**。

**第二刀**：光改异步还不够。18 万个文件就算逐个 await，也要一两分钟；这段时间网关的其它请求确实很慢（实测 `/api/status` 稳定 1.7 秒、偶发 20 秒以上）。是不是 libuv 线程池被遍历占满导致的，我没单独验证，但这段时间和遍历窗口对得上。所以加了门槛 `worthSweeping()`：只有「盘紧」或「上次量到的占用已到上限八成」才去走全树；盘宽裕时启动后也不扫。

**实测**：手跑一次回收，盘余量 1010 MB → 删 27 个旧任务目录、腾出 359 MB → 1422 MB；半小时后 keeper 重新probe，`admission` 从 `allowed:false` 变回 `true`。剩下的 1437 MB 是一小时内的快照（`minAge` 保护），没动。

**顺带记一笔**：快照目录 `~/.allbot/dot/snapshots` 下有 18 万个文件、1.8 GB，平均一个 8 KB。文件手每写一次就整份复制一份，量级不小。上限 5 GB 对一块只剩几 GB 的 C 盘来说太宽松，真要跑长任务得把快照挪到 D 盘。

### 2026-11-27 补：写类动作「还没动手就拒了」不该判死

手机链路验证那条任务：第 3 步把 `recheck.txt` 写出来了（3 字节），第 5 步模型又写了一次，被「文件已存在，要覆盖请传 overwrite=true」拒。产物明明在，任务却判 **failed**。

原因是结算口径按**动作类型**定生死：`files write` 是写类动作（`side_effect=replayable`），失败就算致命。可这次失败发生在落盘之前，磁盘一个字节没变。

改法：`settle.ts` 加一张「事前拒绝」名单——`exists` / `not_found` / `bad_path` / `bad_action` / `parent_missing` / `outside_root` / `symlink_denied` / `content_too_large` / `denied` 这些错误码都是「还没动手就回来了」，按良性算，留痕但不否决。真的写到一半失败（`write_failed`、ENOSPC）照样致命，有专门一条测试钉住。

**验证**：重启后在模拟器上用言出的聊天框发「create final-ok.txt in D:/tmp/alldot-e2e-test」→ 账本出现 `source: mobile` 的任务 → 电脑写出 `final-ok.txt`（3 字节）→ 结算 **done**。同一条任务里第 6 步同样被 `exists` 拒，不再判死。

### 2026-11-27 补：alldot 推不动项目，真正的原因找到了

派了一个「建 add.js + add.test.js，然后跑 node --test」的任务，16 步全是 `desktop`：模型想跑测试，就去点桌面开终端，出了请示卡，卡住。

不是模型笨，是**工人手里没有跑命令的工具**。工人的工具表在 `local-worker.ts` 里写死成：`practice` + `dot_recall` + `skillbook` + `extraHands`（files / desktop / logged_browser / clean_browser / wechat / feishu）。**没有 exec**。

allbot 自己是有 exec 的（`allbot.json` 里 `tools.exec = {security:"full", ask:"off"}`），闸门那侧也早就为它准备好了判档规则（`policy.ts` 的 `DEFAULT_EXEC_WHITELIST`、`judge.ts` 的 `exec_readonly` 一档放行、`exec_workspace_write` 二档）。缺的只是**给工人注册一个走七步壳的 exec 手**。

所以「alldot 能改代码但不能验证代码」：写完文件就收工，测试跑没跑、过没过，它自己不知道，只能靠人看。这是"能优化所有项目"的最后一公里。

**补上了：`src/hands/exec.ts`（命令手）**

- **不带 shell**：命令按空白/引号拆成 argv，`execFile` 直接起可执行文件。`|`、`&&`、`>`、`$(...)` 这些在 exec 手这里只是普通字符，出现就当场拒——没有注入面。
- **白名单**：复用闸门那张 `DEFAULT_EXEC_WHITELIST`（git / node / npm / npx / tsc / eslint / rg / ls / cat / head / tail / pwd / echo / grep / python）。`rm`、`curl`、`powershell` 一律拒。
- **工作区里跑**：`cwd` 只能是任务声明工作区内的相对路径，解析后还要再核对前缀，`..` 跳不出去。
- **判档不自己定**：把命令填进 `GateInput`，交给 `judge`。实测 `node --version` 判 1 档直接跑；`node --test`、`node -e` 这类会执行代码的判 4 档出请示卡——跑测试要点一次同意，这是刻意的。
- 挂了 8 条测试（只读放行、shell 语法拒、白名单拒、cwd 越界、没工作区、非零退出记 failed 步），全仓 696 条全绿。

真机上第一次派任务，工人第 2 步就调了 exec——但参数写成了 `command` 而不是 `cmd`，报「exec 需要 cmd」。已经兼容 `cmd` / `command` / `argv` 三种写法。

**第二层坑**：兼容完还是报同样的错，连试 8 次都一样。根因不在手上，在 `local-worker.ts` 的 `executeHand`：它只把 `args["params"]` 这个**嵌套对象**交给手，模型直接写顶层 `{"cmd":"node --test"}` 时 `req.params` 是空对象。desktop/browser 的手参数 schema 本来就是 `params: {...}`，所以这个坑一直没暴露。现在改成顶层键铺平、嵌套覆盖（`action`/`path`/`content`/`overwrite` 已经单独转交，不重复塞），并加了一条回归测试钉住。

**真机结果**（task_916e…）：第 2 步 `exec succeeded`——工人真的用 exec 跑了一条命令。第 5 步要跑 `node --test`，按设计判 4 档出请示卡。

**还没通的一环**：这张卡批准之后（`status=approved, decided_by=dsbot`），任务**没有回到 queued**，`run_epoch` 还是 0，一直停在 `awaiting_approval`。原因是**桥的 `/api/approvals/answer` 只写 approvals/decisions 两张表**（它从一开始就定了"桥只碰这两张表"），重排逻辑在网关侧的 `routes.ts`。而网关调度器每轮只扫「**过期**」的审批单（`sweepExpiredApprovals`），不扫「已批准但任务还没重排」的单。于是从桥上批准的卡，谁也接不上。

**修法（已做）**：调度器加 `sweepResolvedApprovals()`，每轮扫「状态 approved、任务还在 awaiting_approval / paused」的单，交给已有的 `resumeAfterDecision`。它自己会判「还有别的未决单就先不重排」，已经重排过的任务状态不是 awaiting_approval，下一轮自然扫不到，不会重复 bump epoch。这样不需要让桥多碰一张表，也不用改网关路由。配一条测试：只调 `decideApproval`（模拟桥的做法）→ `tickOnce` 必须把任务补回队列并领走。

**端到端跑通了**（task_4e65d5…，`done`）：

1. 工人用 files 写出 `add.js` / `add.test.js`；
2. 要跑 `node --test` 时判 4 档出请示卡；
3. 桥批准 → 调度器 5 秒内把任务补回队列（epoch 0→1）→ 重跑；
4. exec 真的执行了 `node --test`，`result.txt` 里是真实输出：`✔ add(2, 3) === 5 / tests 1 / pass 1 / fail 0`；
5. 任务结算 `done`。

这是「工人能改代码、也能自己验证代码」的第一个完整闭环。

**代价**：这条任务跑到 `epoch 3`，中间有几步是「崩溃恢复：同一步之前已经成功过，没有重做」——网关重启后的恢复协议把会话判定为中断，任务被重排、重跑了一两轮。产物没错，但白烧了一些 token。恢复协议的重排口径值得再收一收。

顺带记两个这一轮验证到的点：

- 桥的 `/api/approvals/answer` 是可用的（`{id, answer:"agree"|"reject"}`），手机和脚本都能直接下结论，不用等微信。
- 网关启动窗口过后很干净：建任务 HTTP 201 **19 毫秒**。之前那些 40 秒的卡顿集中在启动后的初始化阶段（pricing bootstrap、外网探测等一串 30 秒超时）。

**恢复协议的重排口径收紧了。** 原来 `bumpEpoch` 对 queued / running / awaiting_approval / paused 一律 `run_epoch + 1`。而恢复协议在插件加载时跑一次、`gateway_start` 钩子再跑一次，一次重启能把同一个任务的 epoch 顶到 3，每次重跑都白烧 token。现在只给 `state='running'` 的任务 bump。重启后日志里是 `恢复协议：恢复了 0 个任务，1 个在等你之前的决定（epoch+0，孤儿 0，回队 0）`——不再无脑加一轮。

**契约能表达「测试通过」了（`type: "check"`）。**

之前的交付物只有 file / text / step 三种。想写「测试通过」，只能用 `type:"step"` 表达「有一步 exec 成功」——跑一次就成立，真机里 `node --test` 全挂也照样算交付完，`done` 还是空口的。

现在加第四种：

```json
{ "id": "verify", "description": "单测全过", "type": "check",
  "tool": "exec", "cmd": "node --test", "match": "fail 0", "forbid": "✖",
  "done_when": "exec 跑 node --test 退出码 0 且输出 fail 0" }
```

判定方式：找一条**成功**的 `exec` 步，把它的结果 artifact 解出 `data.cmd` / `data.exit_code` / `stdout`，三个条件都过才算交付：

- `cmd` 里要含声明的命令（防止跑个 `cat` 冒充）；
- `exit_code` 必须是 0（缺这个字段时跳过，兼容老记录）；
- `match` 正则要在输出里、`forbid` 正则不许出现。

没通过时结算不会判 done，而是 paused，`state_reason` 写清原因（「契约没完成：还有 1 个交付物没交（verify）」），工人下一轮的提示词里能看到「跑过 exec「node --test」但没过：退出码 1」。配了 5 条测试（通过 / 非零退出 / 命令对不上 / forbid 命中 / 非 JSON 结果按原文匹配），全仓 **704 条全绿**。

还差一环（未做，记在这）：契约没完成时是 `paused + blocked_on human`，要人点一下才继续。要让它自己接着跑，得给 `blocked_on` 加一个「交付物」类型、并让调度器按有限次数自动回队——这块没动，因为同一条任务里跑测试本来就要人批一次请示卡，自动回队省不了几次点击。

### 2026-11-27 下午：拿 alldot 推真项目，顺着问题做了十轮

派了两条真任务给 alldot（不是演练）：在 `build/dot-core/src/bridge` 上补自我优化的只读接口、在 `src/selfimprove` 上补状态查询函数 + 测试。两条都卡住了，各烧到 120 步和 189 步。卡的过程本身就是证据，下面十条是照现场改的，每条都有测试钉住，全仓从 699 条涨到 **715 条全绿**。

1. **契约能表达「测试通过」**（`type: "check"`）。退出码 0 + 命令对得上 + 输出匹配才算交付，详见上一节。
2. **恢复协议不再一重启就给任务加一轮**。原来对 queued/running/awaiting_approval/paused 一律 `run_epoch + 1`，而恢复协议在加载时跑一次、`gateway_start` 钩子又跑一次。现在只给 `running` 的加。日志里是 `epoch+0`。
3. **同一进程里两份 dot-core 不再各跑一套常驻工作**。网关先 `[gateway]` 后 `[plugins]` 各加载一次（两个 jiti 副本），派发器有账本锁挡着，但恢复协议、30 分钟快照巡检、心跳是两份各跑一遍。现在用 `globalThis` 上一个 symbol 认主份，第二份只挂手和路由，日志写「这份只挂手和路由」；`stop()` 时让出，测试里同一个账本能反复起。
4. **工人新一轮能看见前面做过什么**。批一张请示卡、或者进程崩过一次，任务都会新开一轮，模型手里对话是空的——真机上 54 步全在读文件，批一次卡之后从第 1 步重摸一遍。现在系统提示词带最后 12 步的摘要（命令/路径/输出开头/被拒原因）。
5. **读长文件可以接着读**。`files` 的 read 原来窗口 8000 字符，可 hand 层正文上限是 4000，等于每次都被二次截断、连「截断」那句话都掉，模型以为文件就这么长，只好改用 `tail -n +900` 一段段啃。现在窗口按上限倒推（3400），支持 `offset`，第一行就写「接着读用 offset=N」。
6. **全部步骤都被拒的任务不再判完成**。`denied` / `human_required` 原来被当成「没动手，良性」——一条只会写一个文件的任务，那一步被拒之后仍然判 done，产物根本不存在。现在这两类不算良性，并且加了一条：一步都没成功（replay 跳过的不算）就判 failed。
7. **`wc` 进白名单**。真机上工人想数文件行数，`wc` 被白名单拦了；judge 的只读集合里本来就有它，白名单漏了。
8. **启动时清掉全部 running 工人行**。原来按「半小时没心跳」筛，会把 20 分钟前那次崩溃留下的行留下。加载那一刻这个进程一步活都还没派，所有 running 行都是上一进程的。钩子那次（本进程可能已经有工人在跑）仍按半小时筛。
9. **崩溃恢复跳过重做时把上次的正文带回去**。原来只回一句「结果同上一次，不用再查」——模型要的是内容，拿不到就换个写法再问一遍，真机上在 epoch 3 里连着重试 `cat` / `ls` / `rg --files` 十几步。
10. **结果 artifact 里存一份 summary**。手各自的结果结构只挑字段（files 的正文不在里面），崩溃恢复要回放就只能给空的；现在 `summary`（模型当时看到的正文）也进 artifact。

第 4、5、9、10 条是同一个病：**工人跨轮次没有记忆，而账本里明明记着**。这三处修完，「一轮读文件、一轮批卡、一轮跑测试」这条链才接得上。

第 11 条（顺手）：**exec 拒掉 shell 语法时给出替代写法**。原来只说「这里不经过 shell，一次只跑一条」，真机上模型会换个管道再撞一次。现在直接写「看开头用 `head -n 50`、数行用 `wc -l`、筛行用 `rg 模式 文件`」。

**这一轮 alldot 真交出了东西**：`build/dot-core/src/selfimprove/status.ts`（112 行，只读查询，口径写在文件头）和 `status.test.ts`（3 条测试，代表作的写法和仓库其他模块一致）。单独跑 `node --test src/selfimprove/status.test.ts` 是 3 pass / 0 fail。代价是两条任务分别烧到 120 步和 189 步——上面十条里第 4、5、9、10 条就是照这两条任务的打转现场改的。

第 12 条：**交付物「文件在但早于任务创建」时把理由说清**。原来一律写「磁盘上没有 X（或早于任务创建）」，看着像文件不存在。真机上重派同一件事，文件是上一条任务建的，工人核对完也一样判不认——现在区分「没这个文件」和「有，但不是这次建的（不认）」，人一眼能看出是重派还是没做。

**已知取舍（没改）**：重派同一件事时，文件是上一条任务建的，交付物按「改时间不早于本任务创建」照样不认，任务会停在 paused。这是刻意的——不认旧文件是为了不让「读一遍就交差」蒙混过关。要不要给「续做」单开一条口径（比如 declared 里带 `accept_existing: true`），留给后面定。

### 2026-11-27 晚上：补上「子助手」这一层（多智能体协作）

定稿第 675 行写的是「子助手（写代码）：allbot subagent，父会话是工人」。这套安装里 `api.runtime.subagent` 解析不到（`Unable to resolve plugin runtime module`，worker 头注释第 1 条），`hands/builtin.ts` 又把 `subagents` / `sessions_spawn` 显式拒了。所以这一层一直缺着——不是没做，是当时没路。

现在补在 dot-core 自己身上：**`delegate` 工具**。

- 工人调 `delegate({"brief": "...", "workspace": "..."})`，runtime 就建一条 `parent_id` 指向父任务的任务，起一个**独立的模型循环**去干；
- 子任务有自己的上下文、自己的步骤（记在它自己的任务号下，父任务的账本里只有一条 `delegate` 步骤，标着派了谁）；
- 子任务做完，父工人拿到一句话结论，再决定下一步；
- 边界：只到一层（子工人的工具表里没有 `delegate`）、子任务 15 步上限、子任务里没有人守着所以不许要求人批。
